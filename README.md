大阪拠点のシステムエンジニア。受託・自社プロダクト双方での開発経験を持ち、**モバイルアプリ開発**を主戦場としています。

---

## 現在の業務

レンタルサーバー事業を運営する企業にて、自社プロダクトのモバイルアプリケーション開発に従事。
設計から実装、リリース、運用改善まで一貫して担当しています。

---

## 強み

### 1. 実装者ではなく、プロジェクト責任者としての視点

渡された仕様をそのまま書くのではなく、**そのプロジェクトが最終的に成功するか**を基準に判断します。

- 要件の裏にある目的を確認し、必要なら仕様そのものを提案し直す
- 技術選定を、開発しやすさではなく運用フェーズまで含めたコストで判断する
- 実装前にリスクの所在を洗い出し、詰まりそうな箇所を先に潰す
- スケジュールと優先順位を自分で組み立て、遅延の兆候を早い段階で共有する
- リリース後の保守・引き継ぎを見据えて、コードとドキュメントを残す

Salesforce導入支援の現場では、顧客の業務要件を聞き取り、設計に落とし込み、稼働まで見届ける立場を担ってきました。**一人称で案件を回した経験**があるため、進行管理や関係者との調整を含めて任せていただけます。

技術は目的を果たすための手段であり、判断の軸は常に「この選択が事業にとって正しいか」に置いています。

### 2. モバイル開発のオールラウンダー

モバイル領域については、**主要な選択肢をひととおり実務で扱える**ことが最大の強みです。

| アプローチ | 技術 |
|---|---|
| クロスプラットフォーム | Flutter |
| クロスプラットフォーム | Kotlin Multiplatform（KMP） |
| クロスプラットフォーム | React Native |
| iOS ネイティブ | Swift |
| Android ネイティブ | Kotlin |

「Flutter しか書けない」「iOS しか触れない」といった制約がないため、**要件から逆算して最適な技術を選ぶ**ところから入れます。

- UI の作り込みが要件の中心なら Flutter
- 既存のネイティブ資産を活かしつつロジックだけ共通化したいなら KMP
- Web と人材・コードを共有したいなら React Native
- OS 機能への深い依存やパフォーマンス要件が厳しいならネイティブ

選定理由を説明でき、途中で方針が変わっても対応できます。ネイティブ側も書けるため、クロスプラットフォームで詰まったときにプラットフォームチャネルやネイティブ実装へ降りていく判断も自分で下せます。

### 3. ローカルストレージ・オフライン処理の実装知見

モバイル特有の難所である**端末内データの扱いとオフライン動作**について、強い自信を持っています。

- 端末内データの永続化設計（スキーマ設計・マイグレーション戦略）
- オフラインファーストなアーキテクチャの構築
- 通信断・再接続を前提とした同期処理と競合解決
- バックグラウンド処理、状態復元、キャッシュ戦略

「電波が届かない場所でも動くアプリ」「通信を最小化したいアプリ」といった要件に対して、机上の理論ではなく実装レベルで解を出せます。この領域は後から作り直すコストが大きいため、初期設計から関われると特に価値を出しやすい部分です。

### 4. モバイルの前後もカバーできる技術スタック

| 領域 | 技術 |
|---|---|
| モバイル | Flutter / KMP / Swift / Kotlin / React Native |
| フロントエンド | TypeScript, React, Next.js, Vue.js |
| バックエンド | PHP（Laravel）, Go（gin / echo）, Java |
| インフラ・CI | AWS（EC2 / ECS）, Docker, GitHub Actions |
| Salesforce | Apex / LWC / Visualforce / 各種設定 |

API 設計、認証まわり、CI/CD によるビルド・配信自動化まで含めて話ができるため、**アプリ単体ではなくシステム全体として**の相談が可能です。単体テスト・結合テスト・詳細設計の実務経験があり、品質を担保しながら納品まで走り切ることを重視しています。

### 5. 学習を止めない姿勢

技術の陳腐化が速い領域だからこそ、日常的な学習を習慣にしています。

その結果として、Salesforce認定資格を11種（アプリケーションアーキテクト、データアーキテクト、Sharing and Visibility アーキテクトを含む）、AWS認定（CLF / SAA）を取得。

新しい言語・フレームワーク・プラットフォームへのキャッチアップに抵抗がなく、案件ごとの最適解を選び取ることができます。

### 6. IT以外の視点 ― 行政書士としての法務・許認可知見

関西大学法学部を卒業後、**大阪府行政書士会所属の行政書士**として登録しています。

エンジニアとしては珍しく、以下の領域について実務的な知見を持っています。

- **法務**：個人情報保護、利用規約・プライバシーポリシー、契約実務、著作権・知的財産
- **補助金・助成金**：IT導入補助金、ものづくり補助金など、制度の要件や申請実務
- **IT関連の許認可**：事業立ち上げに伴う各種届出・許認可の要否判断

そのため、単に「言われた仕様を作る」のではなく、

- この機能は法令上そのまま実装して問題ないか
- 規約や同意取得のフローはどう設計すべきか
- この開発に使える補助金制度はないか
- 事業として展開するなら、どの許認可が必要になるか

といった、**技術の外側からの検討**を同じテーブルで行えます。発注側の事業リスクを踏まえた提案ができる点は、他のエンジニアにない価値だと考えています。

行政書士としての専門領域は、**外国人関係の許認可**（在留資格に関する手続きなど）を軸に据えていく方針です。TOEIC L&R 895 の英語力を持ち、英語の技術ドキュメントを日常的に一次情報として読んでいるため、日本語を母語としない依頼者・エンジニアと直接やり取りしながら手続きを進められます。人材の国際化が進むなか、IT業界における外国籍エンジニアの受け入れ支援は、技術と法務の双方を理解している人間が関わる意味の大きいテーマだと考えています。

## What I Bring

### 1. A project owner's perspective, not just an implementer's

I don't simply write what's handed to me. Every decision is measured against whether the project will actually succeed.

- Clarify the purpose behind a requirement, and propose changes to the spec when it doesn't serve that purpose
- Choose technology based on total cost through the operations phase, not on ease of development
- Identify risks before implementation and address likely blockers early
- Own the schedule and priorities, and surface signs of delay while there's still time to act
- Write code and documentation with maintenance and handover in mind

In Salesforce implementation work, I gathered business requirements directly from clients, translated them into designs, and saw projects through to go-live. Having **run engagements end to end**, I can take on progress management and stakeholder coordination as well.

Technology is a means to an end. My decisions are always anchored to one question: is this the right choice for the business?

### 2. An all-rounder in mobile development

My greatest strength in mobile is that I have **hands-on professional experience across all the major options**.

| Approach | Technology |
|---|---|
| Cross-platform | Flutter |
| Cross-platform | Kotlin Multiplatform (KMP) |
| Cross-platform | React Native |
| iOS native | Swift |
| Android native | Kotlin |

Because I'm not limited to a single framework, I can start from the requirements and **work backwards to the right technology**.

- Flutter when polished UI is central to the product
- KMP when existing native assets should be preserved while sharing business logic
- React Native when code and talent are shared with the web side
- Native when deep OS integration or strict performance requirements are involved

I can articulate the reasoning behind each choice and adapt when direction changes mid-project. Since I also write native code, I can decide for myself when to drop down to platform channels or native implementation if the cross-platform approach hits a wall.

### 3. Deep knowledge of local storage and offline handling

I'm particularly confident in **on-device data handling and offline behaviour** — one of the harder problems specific to mobile.

- Local persistence design, including schema design and migration strategy
- Offline-first architecture
- Sync logic and conflict resolution built around dropped and restored connections
- Background processing, state restoration, and caching strategy

For requirements like "it has to work where there's no signal" or "we need to minimise network usage," I can deliver real implementations rather than theory. Since this layer is expensive to retrofit, I add the most value when involved from the initial design.

### 4. Coverage on both sides of the mobile layer

| Area | Technology |

I can discuss API design, authentication, and CI/CD-driven build and distribution automation, which means conversations can cover **the system as a whole rather than the app in isolation**. With professional experience in unit testing, integration testing, and detailed design, I focus on shipping while keeping quality intact.

### 5. Continuous learning

In a field where knowledge goes stale quickly, I've made study a daily habit.

That has resulted in 11 Salesforce certifications (including Application Architect, Data Architect, and Sharing and Visibility Architect) and AWS certifications (CLF / SAA).

I have no hesitation picking up new languages, frameworks, or platforms, which lets me select the right fit for each project.

### 6. A view from outside IT — legal and regulatory knowledge as a certified administrative scrivener

After graduating from the Faculty of Law at Kansai University, I registered as a **certified administrative scrivener (gyoseishoshi), a member of the Osaka Prefecture Administrative Scriveners Association**.

Unusually for an engineer, I have practical knowledge in the following areas:

This means I can bring questions like these to the same table:

- Is this feature lawful to implement as specified?
- How should the terms and consent flow be designed?

Being able to factor in the client's business risk, not just the technical requirements, is value few engineers can offer.

As a scrivener, I'm building my practice around **immigration-related permits and applications**, including status of residence procedures. With a TOEIC L&R score of 895 and a daily habit of reading English technical documentation as a primary source, I can work directly with clients and engineers who don't speak Japanese as a first language. As the workforce continues to internationalise, supporting foreign engineers entering the Japanese IT industry is an area where understanding both the technical and legal sides genuinely matters.
